What it is / 是什么

Four-layer sensitive-data scan (company / machine / personal / confidential) plus falsifiable-claim checks before sharing, listing or publishing any skill, expert pack, document or tool. Use before anything goes outward.

发布质量门禁：发布任何 Skill/专家包/文档/工具到外部（分享、上架市场、对外发布）前后的质量检查。发布前执行四层敏感信息检查（公司信息→本机信息→个人信息→机密信息），发布后按 TRACE 五维（Trust/Reliability/Adaptability/Convention/Effectiveness）执行 AI 自测。发布前另须强制过一道独立专家审（不接受自审自评），并把审查记录登记到发布总账 §四。当用户说'准备发布'、'发布前检查'、'发布后自测'、'TRACE 评测'、'检查一下发布物'、'脱敏检查'、'发布质量'时使用。

When to use it / 什么时候用它

  • 要在对外发布前跑一遍四层脱敏门禁时
  • 要把某条命中定性成误报并留下理由与署名时
  • 要核对基线豁免清单有没有越权放行时
  • 要先把泄漏拦在本地、而不是等平台或第三方发现时

leak-hunter / gatekeeper / secret-scan / leakscan同类的轻量方案：单二进制或零依赖 CLI，扫本地目录、仓库 URL、甚至 git 历史。
  • 守的是发布面，不是凭据召回 —— 对方的核心指标是"密钥有没有漏检"。我们守的是对外发布件的四类面：内部绝对路径、内部主机名与工单号、往来邮件头（Message-ID 等）、内部文档名与代号。密钥只是其中一类。
  • 三层分档，不把提示当命中 —— 硬凭据 / 内部信息 / 提示级（商号疑似只提示）分开计数，所以"有命中"与"要阻断"不是同一件事。同行的输出通常是扁平的严重度列表。
  • 豁免要署名和日期 —— 基线表每条带 name / file / type / matched / reason / reviewer / date，匹配键必须是（文件, 类型, 命中串）三元组。假阳不是"我觉得不是"，是一条可被复核的记录。
  • RC=0 是算出来的，不是看出来的 —— 一次实跑把命中拆成：技术误报 326、规则文本 5、基线豁免 27、真实命中 0。四个数字都在件里，谁也改不了口径而不改数字。

Where they win / 对方强在哪 —— 检测能力。对方有 ML 模型、熵分析、git 历史扫描、甚至拿凭据去厂商接口验证真伪；我们的规则是固定的正则族，召回明显更低，且不扫 git 历史。要查密钥，用它们的；要守发布面并留下可复核的豁免记录，用这个。
