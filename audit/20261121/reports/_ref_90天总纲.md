XLGD 核心资产成熟度与商业化 90 天执行总纲

决策人：Steven Zhao
战略目标：建立开放、可验证、可独立实现、可商业交付的 AI Trust Infrastructure。

一、正式战略决定

我同意将 XLGD 下一阶段战略重心从扩大项目数量转向：

1. 提高核心资产成熟度。
2. 提高外部可验证性和第三方采用能力。
3. 提高开发者接入效率。
4. 建立可交付、可验收、可收费的商业产品。
5. 建立统一战略决策和审批管理机制。

不以仓库数量、代码数量、文档数量、Star 或下载量作为核心成功标准。

以真实技术能力、独立验证、第三方采用、客户交付和实际收入作为主要评价依据。

二、核心资产职责冻结

1. XLGD

总体理论、生态架构、战略方向和治理体系。

2. LGD

治理理论、规则体系、规则生命周期和机器可执行治理原则。

3. UIBC

身份、协议、证据关联、互操作和跨实现验证基础设施。

4. LGD-Eval

Agent、Skill、MCP 等对象的风险评估、证据分析、测试和整改验证。

特别要求：

* Evaluation 不等于 Authorization。
* PASS 不等于绝对安全。
* 自评不等于第三方评测。
* 评分不得自动产生执行权限。
* 默认授权状态为 NOT_GRANTED。

5. SynomosAI

AI Agent Trust & Governance Infrastructure 的工具层、MCP、治理工作流和企业应用。

6. MedXpert

医疗器械法规与行业治理垂直应用，验证 XLGD 在真实专业场景中的商业价值。

以上职责作为当前架构基线。调整边界必须经过单独审查和批准。

三、未来 90 天五阶段执行计划

第一阶段：第 1—15 天

核心资产只读审计与风险清零计划

任务：

1. 审计三个 GitHub 账号的核心仓库。
2. 核实主分支、PR、Actions、发布记录和依赖关系。
3. 核查 UIBC 的证据完整性、互操作性和安全边界。
4. 核查 LGD-Eval 的评分、授权、沙箱和评测可复现性。
5. 核查 MedXpert 的法规来源、更新状态和数据安全。
6. 核查 SynomosAI 的工具权限、执行门禁和发布流程。
7. 核查许可证、署名、版本和公开声明的一致性。

交付：

* 核心仓库资产清单。
* P0/P1/P2 风险清单。
* 已完成、未完成和未验证事项清单。
* 现有 CI 与实际测试证据。
* 整改建议和优先级。

验收：
所有关键结论有仓库、文件、行号或运行记录支撑。
不得将 CI 绿色直接视为安全验收。

第二阶段：第 16—30 天

统一架构与开发者接入设计

任务：

1. 制定 XLGD Reference Architecture。
2. 明确各核心模块的职责和接口。
3. 设计 LGD Rule Registry。
4. 设计统一信任状态模型。
5. 设计 UIBC 版本兼容和弃用政策。
6. 设计 XLGD Conformance Lab。
7. 完成开发者 Quickstart 和最小接入流程。

核心要求：

外部开发者应能独立采用单个模块，不应被迫依赖整个 XLGD 生态。

交付：

* 架构规范。
* 模块接口说明。
* 状态模型。
* 版本政策。
* SDK 和测试入口规划。
* 第三方独立实现指南。

第三阶段：第 31—45 天

最小可售产品准备

优先验证两个商业方向：

A. LGD-Eval

* Agent / Skill / MCP 风险评测。
* 证据化评测报告。
* 风险整改建议。
* 整改后复测。
* 企业私有化评测方案。

B. MedXpert

* 法规知识检索。
* 官方来源追溯。
* 法规时效监测。
* 证据化合规信息。
* 专业场景治理服务。

交付：

* 最小产品定义。
* 产品演示流程。
* 客户使用场景。
* 服务交付边界。
* 初步成本模型。
* 试点验收标准。
* 定价假设。

不等待整个 XLGD 生态完成才开始商业验证。

第四阶段：第 46—60 天

开发者体验与生态接入

任务：

1. 完善 UIBC Quickstart。
2. 提供可运行示例。
3. 建立标准测试向量。
4. 建立兼容性测试流程。
5. 完善 API 文档和错误说明。
6. 设计第三方独立实现验收机制。
7. 梳理 Agent、Skill、MCP 和 CI/CD 生态接入点。

交付：

* 开发者接入文档。
* 最小运行示例。
* 测试工具。
* 兼容性矩阵。
* 第三方采用证据标准。

不将自有账号、自有仓库或同一维护生态内的实现计为独立第三方采用。

第五阶段：第 61—90 天

外部验证与收入验证

任务：

1. 准备真实客户使用场景。
2. 验证 LGD-Eval 服务交付。
3. 验证 MedXpert 行业应用价值。
4. 评估客户愿意付费的功能。
5. 验证部署、支持和维护成本。
6. 收集独立技术反馈。
7. 形成下一阶段产品路线。

交付：

* 外部验证报告。
* 试点结果。
* 客户需求和付费意愿证据。
* 产品定价建议。
* 商业化成本模型。
* 首笔收入执行方案。

所有外部接洽、试点协议、报价、签约、正式提交和公开发布，须经 Steven Zhao 单独批准。

四、建立统一战略决策总账

所有项目必须采用统一记录：

DECISION
OWNER
SCOPE
EVIDENCE
STATUS
ACCEPTANCE
APPROVAL

状态统一：

* PROPOSED：建议事项。
* APPROVED：已批准。
* IN_PROGRESS：执行中。
* BLOCKED：受阻。
* VERIFIED：有证据验证完成。
* RELEASED：已正式发布。

特别规定：

1. APPROVED 不等于 RELEASED。
2. VERIFIED 不等于第三方认证。
3. CI GREEN 不等于质量验收。
4. MERGEABLE 不等于技术合格。
5. SELF-EVALUATION 不等于独立评测。
6. 已提交不等于已采纳。
7. 计划完成不等于实际完成。

五、核心绩效指标

技术成熟度

* P0 风险未解决数量。
* 关键测试通过率。
* 测试跳过及未覆盖数量。
* 评测可复现率。
* 证据链完整性。
* 版本兼容性。

外部采用

* 独立实现数量。
* 外部测试复现数量。
* 第三方集成数量。
* 独立评测者数量。
* 真实生产使用案例。

开发者体验

* 从安装到首次成功运行的时间。
* Quickstart 成功率。
* SDK 覆盖情况。
* 接入失败原因。
* 外部开发者贡献数量。

商业化

* 有效客户需求。
* 产品演示数量。
* 付费试点数量。
* 首笔收入。
* 客户交付成本。
* 续费和持续使用意愿。

所有指标必须保留统计口径和证据来源，不得通过改变口径制造增长。

七、权限与审批红线

未经 Steven Zhao 单独批准：

* 不得合并 PR。
* 不得推送代码。
* 不得修改主分支。
* 不得发布版本。
* 不得部署生产环境。
* 不得修改 LICENSE、版权或署名。
* 不得删除仓库、文件或历史记录。
* 不得代表项目进行外部承诺。
* 不得将关联方评测宣传为第三方认证。
* 不得将准备中的贡献宣传为国际标准采纳。

本文件批准的是战略方向、审计和分阶段准备工作，不自动授权上述外部行动。

八、最终战略目标

建立一个具有以下能力的开放生态：

1. 治理规则可以机器化表达和执行。
2. 身份与证据可以验证和追溯。
3. Agent 风险可以独立评测和复现。
4. 授权和执行具有明确边界。
5. 运行状态可以持续监督。
6. 第三方能够独立实现和互操作。
7. 企业能够部署、使用和购买相关服务。
8. 生态不依赖单一运营方才能持续发展。

最终目标：

让 XLGD 从理论和开源项目集合，发展成为第三方开发者可以独立实现、企业可以实际采用、外部机构可以复核的 AI Trust Infrastructure。

执行原则：

先验证，再整改；先形成最小产品，再扩大投入；先获得真实采用和收入，再扩展生态规模。
