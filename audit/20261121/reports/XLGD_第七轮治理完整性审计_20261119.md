## 3. Rule Registry 架构草案

### 3.1 单条规则的数据模型

```json
{
  "rule_id": "UIBC-S11",
  "version": "1.0.0",
  "domain": "evidence|identity|lifecycle|evidence-anchor|interop",
  "severity": "P0|P1|P2",
  "statement": "包内 JSON 必须 UTF-8、无重复键、无裸控制字符",
  "trigger": {"stage": "verify", "when": "always"},
  "evidence_required": ["serialized_bytes"],
  "machine_check": {"module": "uibc_core.verify", "symbol": "_strict_scan"},
  "tests": {"positive": ["T-S11-P1"], "negative": ["T-S11-N1", "T-S11-N2"]},
  "status": "active|deprecated|proposed",
  "supersedes": null,
  "changelog": [{"version": "1.0.0", "date": "2026-11-19", "note": "从 verify.py 抽出"}]
}
```

### 3.2 双向追踪机制

- **规则→测试**：每个 `rule_id` 必须至少有 1 个正向、1 个负向测试；CI 门禁断言"`tests` 数组非空且用例真实存在"。
- **测试→规则**：测试文件内以 `@rule("UIBC-S11")` 标注；CI 反向断言"每个测试至少标注一条规则"。
- **规则→代码**：`machine_check.symbol` 必须可解析（import 后能取到属性），否则 `BROKEN_LINK`。
- **变更**：规则改版本号 → 旧用例标 `superseded` 但仍保留（回归不可删）。

**验收判据**：`registry validate` 输出 `orphan_rules=0 / orphan_tests=0 / broken_links=0`。

### 3.3 与现有资产的关系
不新建仓库：`rules.json` 放 `uibc-core/policy/`，`skillgate` 三份副本收敛为一份 + 两份 thin shim（先报告，不改）。

## 4. Red Team Benchmark 扩展方案

### 4.1 现状分级（必须先分级，再谈覆盖）

| 类别 | 定义 | 当前 |
|---|---|---|
| **已复现** | 有可执行样本 + 失败输出 + CI 回归 | `F-001…F-009`（9 份）+ `redteam_robustness.py`（CI 常驻） |
| **理论** | 有攻法描述，无样本 | 组合伪造、跨版本降级、时序竞争 |
| **未验证** | 只有传闻或推断 | 评测规避（eval-aware payload） |

### 4.2 扩展三类（对应任务书要求）

1. **多缺陷组合**：现有 CI 已做"14 变异、每对每三元组"（`ci.yml:131-133`，FACT）。扩展：把组合结果写成 `RT-C-xxx` 永久样本，失败即固化为回归。
2. **动态行为**：脚本在"首次运行/第 N 次运行/检测到沙箱后"改变行为。样本形态：延迟触发、环境指纹（`CI=true` 时静默）、分片载荷。
3. **评测规避**：针对评测器本身的对抗——超长注释淹没、Unicode 同形、把危险调用拆到两个文件、`__import__` 字符串拼接。

### 4.3 编号与回归纪律
```
RT-A-001   攻击（已复现）
RT-S-001   静默失败（评测器吞掉错误）
RT-C-001   组合
RT-D-001   动态
RT-E-001   评测规避
```
每份样本必须带：`sample / expected_verdict / actual_verdict / reproduced_at / commit / status(reproduced|theoretical|unverified)`。
**红线**：`status != reproduced` 的样本不得计入"已覆盖"。

## 5. Governance Lifecycle 状态机

```
DRAFT ──register──► REGISTERED
REGISTERED ──evaluate──► EVALUATED ──grant──► AUTHORIZED ──deploy──► RUNNING
RUNNING ──telemetry──► MONITORED ──schedule──► RE-EVALUATING ──pass──► AUTHORIZED
                                                  └──fail──► SUSPENDED
任意状态 ──incident/revoke──► REVOKED ──retire──► RETIRED
```

**允许转换**（部分）：`AUTHORIZED→RUNNING`、`RUNNING→MONITORED`、`MONITORED→RE-EVALUATING`、`REVOKED→RETIRED`。
**禁止转换（必须机器拒绝）**

| 禁止 | 理由 |
|---|---|
| `EVALUATED → RUNNING` | 跳过授权，评测当许可 |
| `REVOKED → AUTHORIZED` | 撤销不可逆，只能重新登记 |
| `MONITORED → AUTHORIZED`（未经 RE-EVALUATING） | 监控不等于复评 |
| `SUSPENDED → RUNNING`（未修复验证） | 事故未闭环 |
| `RETIRED → 任意` | 终态 |

**现状**：`lifecycle.py` 已实现 `TERMINAL` 与 `ONCE_ONLY` 的机器拒绝（FACT），但缺 `EVALUATED/AUTHORIZED/RUNNING/MONITORED/RE-EVALUATING` 五态 → 中段是断的。

## 6. 第三方独立验证规范

### 6.1 四档命名（严禁混用）

| 档 | 定义 | 允许的表述 | 禁止的表述 |
|---|---|---|---|
| **S 自评** | 同一维护者 | "self-reported" | "verified" |
| **A 关联方** | 有合同/雇佣/资助关系 | "affiliated review" | "independent" |
| **I 第三方** | 无利益关系、独立执行 | "independent third-party run" | "certified" |
| **C 认证** |  accredited body 出具 | "certified" | — |

**当前实况**：S 有、A 有（自有多个账号互相跑）、I = 0、C = 0。

### 6.2 盲测协议（最小可执行）
1. 交付物：语言中立向量包（JSON）+ 独立验证工具（不 import 主实现）+ 期望结果表（先不公开答案）。
2. 执行方：外部方在自己环境跑，回传 `external_node_result.json`（含 `os/python/commit/时间/逐项结果`）。
3. 判定：与期望表比对；分歧记录为 `dispute`，不修改期望表去迁就结果。
4. 只有回传文件 + 非本机环境指纹，才计 **I 档**。

### 6.3 利益冲突披露（必填字段）
`reviewer / affiliation / funding / employment / prior collaboration / conflict_declared(true|false) / signed_at`
缺任一项 → 不计第三方。
