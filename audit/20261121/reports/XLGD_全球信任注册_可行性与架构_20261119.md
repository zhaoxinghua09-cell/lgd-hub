## 0. 本轮做了一次真实的可行性实验

任务书的场景是：**Agent 在平台 A 注册、在平台 B 评测、在平台 C 被调用，C 不依赖 B 的内部数据库也能验证。**

这个场景可以用现有原料在本地模拟（不联网、不建服务）：
`proposals/p23_global_registry/feasibility_demo.py` → **10 用例全部符合预期**（`evidence/p23_feasibility.json`）

### 0.1 结论：五项属性，四项可离线验，第五项（撤销）没有来源

| 属性 | C（无 A/B 数据库）能否验证 | 依据 |
|---|---|---|
| 身份 | ✅ 可验 | 本地钉扎的指纹比对 |
| 证据完整性 | ✅ 可验 | 自带签名 + 规范化哈希重算 |
| 评测结果与版本 | ✅ 可验 | 报告自带 rule/engine 版本，对照公开兼容表 |
| 授权有效性 | ✅ 可验 | 授权对象自带 scope/expires + 签发者签名 |
| **撤销状态** | ❌ **不可独立判断** | 今天没有任何公开撤销源 |

**第五项才是全局注册存在的理由。** 前四项靠"自带护照"就能验——这解释了为什么"注册中心"不是必需品，而"公开撤销源"是。

### 0.2 一个必须看的演示：D10

| 用例 | 场景 | 结果 |
|---|---|---|
| D7 | 已撤销 + 快照新鲜 | DENY ✅ |
| D8 | 撤回快照 30 小时未更新 | DENY（fail-closed）✅ |
| D9 | 完全没有撤销源 | DENY ✅ |
| **D10** | **宽松实现把快照有效期放到 30 天** | **ALLOW** ⚠️ |

D10 的 "PASS" 不是好消息——它是我**故意**构造的错误实现，用来证明：**只靠快照、不做时效约束，撤销会静默失效**。这正是全局注册要解决的核心风险。

## 2. 架构设计（避开"再造一个中央库"）

### 2.1 三条设计原则（从实验反推出来的）

1. **护照优先，注册为辅**：身份/证据/评测/授权四项靠 bundle 自证，注册中心只提供两个东西——**唯一标识解析** 与 **撤销源**。
2. **撤销必须公开可取**：C 若拿不到撤销状态，只能永远 DENY（可用性归零）或信任陈旧快照（安全性归零）。没有第三条路。
3. **不做联邦也要能验**：离线 verify 已成立，所以"运营方停服仍可验证"这条底线不用新建任何服务就能守住。

### 2.2 三层结构

```
┌─ L3 互操作层 ─  passport bundle 格式（gtp/1）+ 兼容表 + 跨平台一致性测试
├─ L2 服务层 ───  resolver（标识→当前状态）+ revocation feed（撤销源）
└─ L1 自证层 ───  identity / evidence / evaluation / authorization 自带签名，离线可验
```

**关键取舍**：L2 只承载"会变的状态"（是否撤销、当前版本）。**不变的东西不放进注册中心**——放进去只会变成又一个需要同步的库。

### 2.3 Passport Bundle（草案，复用本轮实验格式）

```json
{
  "bundle_version": "gtp/1",
  "identity":      {"agent_id": "...", "key_fp": "...", "version": "...", "status": "REGISTERED"},
  "evidence":      {"...": "...", "mac": "..."},
  "evaluation":    {"score": 91, "rule_version": "rules/2", "engine_version": "engine/3",
                    "evaluator": "platform-B", "mac": "..."},
  "authorization": {"subject": "...", "scope": [...], "expires_at": "...", "issuer": "...", "mac": "..."},
  "revocation":    {"revoked": false, "checked_at": "...", "source": "..."}
}
```

**四个签名缺一不可**：证据由 A 签、评测由 B 签、授权由授权者签、撤销由撤销源签。任何一个签名缺失，C 就只能猜。

## 4. 六个 WP 的设计要点

### 4.1 WP1 Global Entity Registry

唯一标识建议：
```
entity_id = "uibc:" + base32(sha256(canonical(creator, name, first_version)))[0:22]
```
**关键约束**：标识由 (创造者, 名称, 首版本) 决定，**与后续版本无关**——版本是属性，不是身份。这样"换版本不换身份"和"换创造者必须换身份"同时成立。

注册状态机（比现有 `REGISTERED` 单值扩展）：
```
REGISTERED → EVIDENCE_LINKED → ACTIVE ⇄ SUSPENDED → REVOKED → EXPIRED
```
**撤销不可逆**（只能重新登记），**EXPIRED 可经复评回到 ACTIVE**。

### 4.2 WP2 Trust Query API

六个查询统一为"返回状态 + 证据指针"，**任何情况都不返回空对象**：

| 查询 | 返回 |
|---|---|
| `resolve(entity_id)` | `{status, current_version, aliases, gone_since?}` |
| `evidence(entity_id, version)` | `{state, digests[], issued_at[]}` |
| `evaluation(entity_id, version)` | `{score, rule_version, engine_version, report_digest}` |
| `authorization(entity_id, scope)` | `{granted: bool, expires_at, issuer}` |
| `revocation(entity_id)` | `{revoked, at, reason, source_sig}` ← **必须签名** |
| `delegation(entity_id)` | `{chain[], depth, valid}` |

**必须先有签名**：撤销查询若不签名，C 无法区分"真的没撤销"与"中间人改了响应"。

### 4.3 WP3 Evidence Interoperability

现有 `repro_kit` 可直接扩：加"评测报告交换"章节（score + rule/engine + evaluator 签名 + 语料版本）。跨平台一致性测试沿用同一套向量，两个实现各跑一遍结果 diff。

### 4.4 WP4 Trust Provider Ecosystem

五类提供者的准入（先文档，**不开放**）：

| 类型 | 准入要求 | 责任边界 |
|---|---|---|
| 身份服务商 | 钉扎公钥可分发的渠道 + 撤销源 | 只对"我登记过"负责 |
| 评测服务商 | 公开方法 + 语料版本 + 引擎版本 | 只对"按公开方法的结果"负责 |
| 独立验证者 | 利益冲突披露齐全 | 只对"我跑过"负责 |
| 证据提供者 | 采集环境 + 完整性签名 | 只对采集范围负责 |
| 行业应用者 | 不改协议语义 | 只对自己产品负责 |

### 4.5 WP5 Reputation & Anti-manipulation

**这一块最容易做成"又一个评分系统"，必须克制**：
- 评分**只描述证据质量**（完整性、可复现性、时效），**绝不映射为授权**
- 利益冲突披露 7 字段（reviewer/affiliation/funding/employment/prior collaboration/conflict_declared/signed_at），缺一不计
- 虚假注册识别：同一 creator 名下大量无证据实体 → 标记 `UNVERIFIED_CLUSTER`，不自动封禁
- 操纵防护：**不提供公开的"好评"接口**，避免刷分；只提供"是否可验证"的二元结果

### 4.6 WP6 Open Governance

RLP 流程（沿用前轮设计）+ 一条硬规则：**有未解决反例不得进入 ACCEPTED**。S4/V4、S5/V5 那个真实分歧应作为第一个 RLP 案例登记。
