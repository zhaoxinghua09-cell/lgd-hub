# demo · 五分钟自验

门户写着「不要求你相信，只提供你能自己跑一遍的证据」。这个目录就是那个「跑一遍」。

## 跑什么

一条命令：

```bash
python demo/verify.py
```

它会：

1. 把参考实现 `uibc-core` 克隆到临时目录；
2. 切到门户锚定的那个 commit（`73f31cc`）；
3. 跑门户上写的三条命令；
4. **自动比对**门户写的三个数字（151 / 7 / 70）；
5. 打一张表，任何一项不符就非零退出，跑完把临时目录清掉。

不需要装任何依赖，只要 Python 3 和 git。

## 预期输出（2026-10-23 本机实跑）

```
当前 commit：73f31cc（页面锚定 73f31cc）

检查                实测    应得    退出码  判定
unittest         151   151      0  PASS
stress             7     7      0  PASS
cross_check       70    70      0  PASS

[PASS] 三条命令全部复现，数字与页面一致：151 / 7 / 70
       页面还写着「同 commit 的 CI 亦为绿」，CI 记录：
       https://github.com/zhaoxinghua09-cell/uibc-core/actions/runs/39159391899
```

耗时约 25–40 秒（视网络与机器）。

## 它凭什么可信——负对照

一个只会打 PASS 的脚本不值得信。把这个脚本里的期望值改错（例如把 151 改成 999），它会：

```
unittest         151   999      0  FAIL
[FAIL] 1 项与页面所写不符 —— 页面上的数字在这一版上不成立
```

退出码 **1**。也就是说：**它有能力说「不」**。

## 为什么期望值写死在脚本里

三个数字故意**不**从 `world.json` 读取。理由：如果脚本跟着源文件走，源文件被改错时脚本会一起错，就失去「独立复现」的意义。写死 + 与页面比对，才叫第三方核验。

## 其它用法

```bash
python demo/verify.py --keep            # 保留克隆目录，自己再翻
python demo/verify.py --dir <path>      # 用已有的 uibc-core 克隆（省一次 clone）
```

## 没覆盖什么

- 只验 `uibc-core` 那三个数字；技能数（109 / 81）、域论文（13）、静默失效模式（14）、SWHID、Rekor 条目、DOI **不在本脚本内**；
- 那些要么需要公开登记库（DataCite / SWH / Rekor），要么需要遍历另一个仓库，属于 `PREDELIVER.md` 里另外几项。
