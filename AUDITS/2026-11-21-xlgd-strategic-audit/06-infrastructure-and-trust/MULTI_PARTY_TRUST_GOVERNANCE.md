# MULTI_PARTY_TRUST_GOVERNANCE（多方信任与利益冲突治理 · 2026-11-21）

> 核心命题：**五类"看起来像验证"的结果，必须被强制分类，不得混为一类。**
> 现状（V）：本生态产出的 100% 是第 1 类（作者自评）与第 2 类（商业付费）的混合，第 3–5 类为 0。

## 一、五类结果（不可合并）

| 类 | 定义 | 谁产出 | 可对外强度 | 现状 |
|---|---|---|---|---|
| **R1 作者自评** | 作者用自己工具评自己对象 | 作者 | 最高 `TESTED` | **主力**（含"自评 100/A+"） |
| **R2 商业付费评测** | 客户付费，评测方出结论 | 评测方 | 可 `VERIFIED`，但必须披露付费关系 | 0（尚无客户） |
| **R3 第三方独立评测** | 与作者无雇佣/合作关系 | 独立方 | `VERIFIED`（可作背书） | **0** |
| **R4 社区测试** | 匿名/多人复跑 | 社区 | `TESTED`（聚合算 MEDIUM） | 0 |
| **R5 正式认证** | 有资质机构 | 认证机构 | 可称"认证" | **0，且我们无权做** |

**硬规则**：任意输出必须带 `result_class: R1|R2|R3|R4|R5`。缺省为 R1。

## 二、九项机制设计

| 机制 | 设计要点 | 现状 |
|---|---|---|
| 多验证者 | 同一对象允许多条结果并存，不合并成"综合结论" | 0 验证者 |
| COI 披露 | `affiliated_with_author` / `paid_by_subject` / `paid_by_author` 三字段 | 设计有，实现无 |
| 规则透明 | 规则 ID + 版本 + 权重公开（当前权重未公开） | 部分 |
| 结果申诉 | `dispute` 事件挂原结论旁，不删 | 无 |
| 证据复核 | 任何人可跑 kit 复算 | **有（kit）** |
| 验证者信誉 | 历史结果 + 被推翻次数（公开） | 无 |
| 结果撤销 | `REVOKED` + 原因 + 时间，保留历史 | 无 |
| 版本历史 | 结果绑定 version + fingerprint，旧结果标 `SUPERSEDED` | 无 |
| 争议解决 | 三步：技术复现 → 规则解释 → 公开记录分歧（不强行统一） | 无 |

## 三、四个"不得"（对应指令要求）

1. **作者不能既是唯一规则制定者，又是唯一验证者**；
2. **商业伙伴不能影响 verdict**（合同必须写）；
3. **付费评测必须公开付费关系**（否则等同 R3 冒充）；
4. **不能把"多个账号"当成"多方"**（本生态 4 账号同人，V）。

## 四、当前最严重的结构性冲突（3 条，V）

| 冲突 | 事实 | 解法（低成本的） |
|---|---|---|
| 规则 owner = 唯一维护者 = 唯一验证者 | 三者同一人 | 先把"验证"外放（kit + 邀请），规则变更公开差异表 |
| 自评数字被用作对外证据 | `benchmarks/README.md` 100/A+ vs 实测 86/A | 所有对外数字标注来源与样本量 |
| 评测与商业同体 | 未来"付费审计"与"评测"同一人 | 用 `result_class` 区分，商业交付写"advisory" |

## 五、争议处理流程（可直接用）

```
1. 提出 dispute（对象 fingerprint + 质疑点 + 反证链接）
2. 双方各自跑 kit / 规则，公开命令与输出
3. 若分歧源于规范歧义 → 进 SPECIFICATION_ATTACK_REPORT（作为规范问题）
4. 若源于实现差异 → 记录在兼容性矩阵
5. 不强行统一结论；两条结果并存，标注争议
```

## 六、验收判据

1. 任一结果可读 `result_class` 与 `coi` 三字段；
2. 存在至少一条"作者以外的签名结果"（当前 0）；
3. 撤销与申诉有事件记录、不删历史；
4. 商业合同中写明"不影响技术结论"。

> 诚实条款：以上除"证据复核（kit）"外，全部为设计；五类结果中 R3/R4/R5 为 0。
