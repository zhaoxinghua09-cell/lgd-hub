XLGD 第九轮执行任务：统一事实来源、证据管理与跨项目运营系统

决策人：Steven Zhao

执行性质：只读盘点、管理系统设计、自动化方案准备。

未经单独批准，不得修改仓库、合并 PR、推送代码、发布、部署或开展外部行动。

一、建立 Asset Registry

覆盖三个 GitHub 账号及所有核心项目。

每个仓库记录：

1. 账号及仓库名称。
2. 项目所属核心资产。
3. 默认分支。
4. 最新主分支 SHA。
5. 最新提交时间。
6. 最新 Release 和 Tag。
7. 当前开放 PR。
8. 当前未解决 Issue。
9. 最近 CI 运行结果。
10. 许可证。
11. 维护状态。
12. 负责人。
13. 关键依赖。
14. 当前风险等级。

区分活跃仓库、归档仓库、Fork、实验项目和正式产品。

二、建立 Evidence Ledger

所有关键技术结论必须关联证据。

至少包括：

* 证据编号；
* 对应项目；
* 证据类型；
* 来源；
* 产生时间；
* 对应代码 SHA；
* 测试命令；
* 测试环境；
* 测试结果；
* 复核状态；
* 已知限制。

没有可追溯证据的结论标记 NOT VERIFIED。

三、建立 Public Claims Ledger

盘点 README、网站、GitHub Topics、论文、标准贡献文件和公开宣传材料中的技术声明。

重点检查：

* 测试数量；
* 性能数据；
* 安全能力；
* 第三方采用；
* 独立实现；
* 标准提交与采纳；
* 评测等级；
* 产品成熟度；
* 法规覆盖范围。

每项声明必须关联来源、日期、适用范围和限制条件。

发现过期或夸大的声明，只提出修改建议，不自行修改公开内容。

四、建立 Dependency Map

识别：

* 仓库之间的代码依赖；
* 协议依赖；
* 数据依赖；
* 外部 API 依赖；
* 发布依赖；
* CI/CD 依赖；
* 商业产品依赖。

对关键依赖进行故障传播分析，确定单点故障和版本不兼容风险。

五、建立 Evidence Lifecycle

对评测、证据和授权记录明确：

* 生成；
* 验证；
* 生效；
* 过期；
* 撤销；
* 复核；
* 重新评测。

不同对象的有效期必须有明确依据，不得统一假设所有证据具有相同有效期。

六、建立 Execution Dashboard

每项工作记录：

* 目标；
* 负责人；
* 优先级；
* 预计成本；
* 实际成本；
* 当前状态；
* 完成证据；
* 验收标准；
* 阻塞原因；
* 下一步。

每周统计 P0/P1 风险、核心资产进展、商业交付进展和需要 Steven Zhao 审批的事项。

七、最终交付

1. 三个 GitHub 账号的核心资产总表。
2. 核心仓库事实基线。
3. 关键证据索引。
4. 对外声明核查表。
5. 跨项目依赖关系图。
6. 证据生命周期规范。
7. 项目执行仪表盘设计。
8. 未来 30 天最优先任务。

所有结论区分 FACT、INFERENCE、NOT VERIFIED、BLOCKED。

禁止将文档记录当成实际运行证据，禁止将同一维护生态的成果算作独立第三方采用。

本轮先完成盘点和设计，提交报告后等待审批。
